2. TASK 2 REQUIREMENT SUMMARY (verbatim from assignment PDF)
================================================================

BUSINESS OUTCOME: Connect a scheduled port call to its vessel and cargo
instead of reading files in isolation.

Display registered vessels, ask for a vessel name and a reference date in
YYYY-MM-DD format. Remove surrounding spaces from the name and match it
case-insensitively. Filter port calls to that vessel, then locate the
earliest call on or after the reference date. Load the matching manifest
through call_id, then resolve every shipment_id against dataset/shipments.
Print the call, totals and cargo lines in manifest order. A missing
shipment is listed as MISSING RECORD and counted separately. If several
calls share the earliest date, choose the call with the alphabetically
smallest call_id. For an invalid date, print
"Error - Date must use YYYY-MM-DD." and repeat only the date prompt. For an
unknown vessel, print "Vessel not found." If no qualifying call exists,
print "No upcoming port calls found." If the selected call has no readable
valid manifest, print "Manifest unavailable." In these three cases, return
to the menu.

Exact example output (client contract — copy verbatim, only the data
varies):
  Vessel name: Nordic Relay
  Manifest for Nordic Relay | Call HFL-GOT-2048 | 18 October 2026
  1. SHP-1042 | Norra MedTech AB | 860.0 kg | REFRIGERATED
  2. SHP-1051 | MISSING RECORD
  Declared shipments: 2
  Resolved weight: 860.00 kg
  Missing shipment records: 1

Notes on the exact format (client contract, byte-for-byte aside from
variable data):
- "Vessel name: " is the input prompt echo shown in the transcript (the
  program's actual input() prompt string; not itself a print()).
- Header line: "Manifest for {vessel name as stored, e.g. proper case from
  the vessel record} | Call {call_id} | {D Month YYYY}" — single spaces
  around each "|", literal "Manifest for " and " | Call " tokens.
- Each cargo line: "{n}. {shipment_id} | {customer} | {weight_kg} kg |
  {cargo_type or NOT PROVIDED}" for a resolved shipment, using 1-based
  manifest-order numbering; OR "{n}. {shipment_id} | MISSING RECORD" for an
  unresolved shipment_id — note the missing-record line has only two
  "|"-delimited segments (index+id, then the literal token), not four.
- weight_kg is printed as its raw/natural value (the example shows "860.0
  kg", i.e. Python's default float-to-string rendering, not forced to two
  decimals on this line — contrast with the summary's "Resolved weight"
  line below, which IS forced to two decimals).
- "Declared shipments: {n}" = len(manifest["shipment_ids"]), counting every
  entry regardless of whether it resolved.
- "Resolved weight: {sum:.2f} kg" = sum of weight_kg over only the
  successfully resolved shipments, formatted to exactly two decimal places
  (":.2f"), even though individual cargo lines above are not forced to two
  decimals.
- "Missing shipment records: {n}" = count of shipment_ids with no matching
  shipment file/record, i.e. Declared shipments - (number of resolved
  cargo lines).
- Error strings, printed verbatim with no extra text:
    Error - Date must use YYYY-MM-DD.
    Vessel not found.
    No upcoming port calls found.
    Manifest unavailable.
- Optional-field handling (from DATA-DICTIONARY.md, applied to each
  resolved shipment): missing/absent hazardous or temperature_controlled
  is treated as false; missing/absent cargo_type prints the literal token
  "NOT PROVIDED" in the cargo_type position of the cargo line.

3. PROPOSED DESIGN
================================================================

Module responsibilities (use the shared interfaces in
INTEGRATED-CONTRACT-PLAN.md):

data_access.py:
- load_vessels(directory) -> shared LoadResult
    Reuse the shared valid records and structured diagnostics defined in
    INTEGRATED-CONTRACT-PLAN.md to display vessels and resolve the typed
    vessel name. Do not add a second vessel parser.
- load_port_calls(path) -> shared LoadResult
    Reads port_calls.csv through the common CSV loader, validates its
    required header, preserves arrival_date source strings and row context,
    and propagates fatal CSV/schema/I/O errors. Each operation validates
    full dates independently so one invalid row does not suppress others.
- load_manifests(directory) -> shared LoadResult and
  load_shipments(directory) -> shared LoadResult
    Load each directory once in sorted source-path order. Operations select
    records by their internal IDs, never by filenames. A manifest is usable
    only when its call_id and vessel_id match the selected call and its
    required shipment_ids/event_codes are string lists. Shipment lookup
    selects the first valid matching shipment from the one loaded result.
    Keep all diagnostics attached to the results. If no usable matching
    manifest exists, Task 2 prints the exact "Manifest unavailable."
    message; unresolved shipment references print/count "MISSING RECORD".

operations.py:
- parse_reference_date(text) -> datetime.date | raises ValueError
    Validate exact YYYY-MM-DD shape and a real date before returning
    datetime.date; any ValueError is caught by the caller (main.py's prompt
    loop) to print
    "Error - Date must use YYYY-MM-DD." and re-prompt only for the date
    (the vessel name is not re-asked).
- resolve_vessel(name, vessels) -> dict | None
    Trims name.strip(), compares against each vessel["name"].strip() using
    .casefold() equality (not substring/partial match), returns the first
    match or None. Returns None -> caller prints "Vessel not found." and
    returns to menu.
- select_call(calls, vessel_id, reference_date) -> dict | None
    Filters calls to matching vessel_id, then to those whose arrival_date
    parses as a valid calendar date (invalid dates such as
    HFL-BAD-9999's "2026-02-30" are excluded here via a try/except around
    the per-row date parse — an unparseable row is treated as "not a
    candidate," never as a crash) AND parsed_date >= reference_date. If the
    resulting candidate list is empty, returns None (caller prints
    "No upcoming port calls found." and returns to menu). Otherwise returns
    min(candidates, key=lambda c: (parsed_date(c), c["call_id"])) — i.e.
    earliest arrival_date first, alphabetically smallest call_id breaks any
    tie on date. This is a pure function over already-loaded data, easily
    unit-testable with constructed tie-producing fixtures independent of
    the shipped dataset.
- build_manifest_report(vessel, call, manifest, shipment_records)
      -> dict (or a small dataclass/named tuple) containing: vessel name,
    call_id, formatted date string, an ordered list of per-line results
    (each either a resolved-shipment tuple or a MISSING_RECORD marker),
    declared_count, resolved_weight_total, missing_count. Iterates
    manifest["shipment_ids"] in file order (not resorted), selecting each ID
    from the shared `load_shipments(...).records`; on no match, appends a
    MISSING_RECORD marker and increments missing_count; on a resolved
    record, applies optional-
    field defaults (hazardous = record.get("hazardous", False),
    temperature_controlled = record.get("temperature_controlled", False),
    cargo_type = ("NOT PROVIDED" if record.get("cargo_type") is None
                  else record["cargo_type"])) and adds
    weight_kg to resolved_weight_total. This function is pure
    business logic (no print()), so it stays unit-testable; main.py (or a
    thin operations.py print helper) is responsible for the actual
    print() calls using the exact strings from Section 2.
- format_call_date(arrival_date_str) -> str
    datetime.date.fromisoformat(arrival_date_str).strftime("%d %B %Y"),
    then strip a leading zero from the day (e.g. "18 October 2026" not
    "18 October 2026" with a leading 0 — %d zero-pads to "08" for single-
    digit days, so a leading-zero strip such as
    result.lstrip("0") applied only to the day portion, or building the
    string manually as f"{date.day} {date.strftime('%B %Y')}", is required
    to match the example's un-padded day). This helper is also the natural
    reuse candidate for Tasks 5/8 if they need the same "D Month YYYY"
    presentation.

main.py:
- In the `elif selection == 2:` branch: (1) load vessels, calls, manifests,
  and shipments through the shared result contract, retaining all
  recoverable diagnostics for task-appropriate reporting; load and print
  the registered
  vessels list (reusing Task 1's exact display, per spec's "Display
  registered vessels" instruction — this is not a new format, it is a call
  into whatever Task 1's implementation exposes); (2) prompt
  "Vessel name: ", trim+resolve via operations.resolve_vessel — on None,
  print "Vessel not found." and fall through to the outer menu loop
  (`continue`/normal fallthrough, no re-prompt); (3) loop prompting for the
  reference date until parse_reference_date succeeds, printing
  "Error - Date must use YYYY-MM-DD." and re-prompting on each failure
  (this inner loop is scoped to the date only, per spec's "repeat only the
  date prompt"); (4) call operations.select_call — on None, print
  "No upcoming port calls found." and return to menu; (5) select the first
  usable manifest matching both call_id and vessel_id from the shared
  manifest records — if none, print
  "Manifest unavailable." and return to menu; (6) build and print the full
  report via operations.build_manifest_report, formatting each line exactly
  per Section 2.
- The date sub-loop catches only ValueError from the user's date input.
  Recoverable record diagnostics remain available to operations; fatal
  source/CSV/schema/I/O errors propagate to an explicit, narrowly scoped
  service error path. Do not use a blanket `except:` or show an empty
  successful report after a fatal loader error.

Tie-break logic (explicit, restated): sort key =
(parsed_arrival_date, call_id) ascending; Python tuple comparison already
implements "earliest date first, then alphabetically smallest call_id" in
one expression, so no separate two-pass sort is needed.

Shipment resolution and MISSING RECORD counting (explicit, restated):
declared_count = len(shipment_ids) as listed in the manifest (order
preserved); for each id, exactly one of (resolved -> add to resolved list,
add its weight_kg to the running total) or (not resolved -> add a
MISSING RECORD marker, increment missing_count) happens; at the end,
missing_count must equal declared_count - len(resolved list) as an internal
consistency check the implementer can assert in tests.

Optional-field defaults (explicit, restated): hazardous and
temperature_controlled default to False when the key is absent OR present
as JSON null (same "absent-or-null both fail to a default" treatment used
for Task 1's required-field validation, applied here to optional booleans
instead of rejecting the record); cargo_type defaults to the literal string
"NOT PROVIDED" when the key is absent OR its value is JSON null, while an
empty string remains valid string data and is preserved.

6. INTEGRATION CONTRACT UPDATE
================================================================

Use INTEGRATED-CONTRACT-PLAN.md as the canonical shared interface. It
supersedes this plan's provisional tuple/count loader shapes and any
silent-swallowing alternatives. Directory loaders return valid records
plus structured diagnostics; recoverable malformed records are skipped
with diagnostics, while fatal directory, CSV, schema, and I/O errors
propagate explicitly. load_json reads one JSON object and propagates
single-file errors.

The port-call loader retains source arrival_date strings, and Task 2 parses
dates in its operation. Select the earliest valid call on or after the
reference date, breaking equal-date ties by ascending call_id. Empty
shipment_ids and event_codes lists are valid; a missing shipment reference
still prints/counts MISSING RECORD in manifest order. A matching manifest
must be valid under the shared record shape; if none is usable, retain the
exact mandated "Manifest unavailable." output. Paths come from the common
project root, not the process working directory.
