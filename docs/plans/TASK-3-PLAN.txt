Design considerations (not a review approval):
The design below (Section 3) implements the classification rule table as a
single if/elif/elif/else chain in exactly the table's stated order —
hazardous, then temperature_controlled, then (priority == EXPRESS or
weight_kg >= 5000), then the STANDARD fallback — so that FIRST-MATCH
semantics are structurally guaranteed rather than merely intended: once an
earlier branch's condition is true, no later condition is ever evaluated,
which is the only way to satisfy "classify every resolved shipment using the
FIRST matching rule" when a shipment could satisfy more than one row (e.g. a
shipment with hazardous=true AND temperature_controlled=true must resolve to
CONTROLLED, never COLD CHAIN — reasoned through in Section 4 since
no shipment in the shipped dataset has both flags true simultaneously). The
function is pure: classify_shipment(shipment: dict) -> tuple[str, str] reads
only its single dict argument, performs no I/O, no printing, and no mutation
of its input, and returns a (category, reason) pair — satisfying the
engineering note verbatim and making it trivially unit-testable against
constructed fixtures independent of the shipped dataset.

2. TASK 3 REQUIREMENT SUMMARY (verbatim from assignment PDF)
================================================================

BUSINESS OUTCOME: Turn raw shipment attributes into a documented operational
decision.

Ask for a call ID, remove surrounding spaces and match it case-insensitively.
For that call, classify every resolved shipment using the FIRST matching
rule below. Print the category and reason in manifest order, then summarize
counts by category in the stated order. If the call is unknown, print
"Port call not found." If its manifest is missing or malformed, print
"Manifest unavailable." In either case, return to the menu.

Rule table (exact order — first match wins):
  1. hazardous is true                              -> CONTROLLED
  2. temperature_controlled is true                  -> COLD CHAIN
  3. priority is EXPRESS or weight_kg >= 5000         -> EXPEDITE
  4. otherwise                                        -> STANDARD

Example output (client contract — copy verbatim, only the data varies):
  SHP-1045 | EXPEDITE | express service
  SHP-1046 | CONTROLLED | hazardous cargo
  SHP-1067 | EXPEDITE | express service
  Category totals: CONTROLLED=1, COLD CHAIN=0, EXPEDITE=2, STANDARD=0

Reason strings are short lowercase phrases per category. The assignment
gives two verbatim: "hazardous cargo" (CONTROLLED) and "express service"
(EXPEDITE). This plan infers the remaining two in the same style:
"temperature controlled" (COLD CHAIN) and "standard handling" (STANDARD).

ENGINEERING NOTE (verbatim): Make classification a pure function that
receives one shipment dictionary and returns both category and reason. Rule
order is business policy and must be visible in the code.

Error strings, printed verbatim with no extra text:
  Port call not found.
  Manifest unavailable.

Per-line format (inferred from the example, one line per RESOLVED shipment,
in manifest order): "{shipment_id} | {CATEGORY} | {reason}" — single spaces
around each "|". No line is printed for an unresolved shipment_id (see
Section 3 for why this differs from Task 2's MISSING RECORD line).

Summary line (verbatim format from the example): "Category totals:
CONTROLLED={n}, COLD CHAIN={n}, EXPEDITE={n}, STANDARD={n}" — all four
categories always printed, in that fixed order, even when a count is 0.

Prompt string: the assignment's example output block does not show an
input() prompt line the way Task 2's transcript showed "Vessel name: ", so
no prompt string is a confirmed client contract for Task 3. This plan
proposes "Call ID: " as a sensible default (matching Task 2's "{Field}: "
style) but flags it as NOT independently verified against the PDF's own
transcript the way "Vessel name: " was for Task 2.

3. PROPOSED DESIGN
================================================================

Module responsibilities use the shared contract for loading, with
task-specific classification and output behavior:

data_access.py (shared contract):
- Use `load_port_calls`, `load_manifests`, and `load_shipments`, each
  returning the shared `LoadResult`. Keep their diagnostics available to
  the service. Operations select records by internal IDs, not filenames;
  recoverable record/file errors are diagnosed, while fatal directory and
  I/O failures propagate.

operations.py:
- resolve_call(call_id_text, calls) -> dict | None
    call_id_text.strip().casefold() compared against each
    call["call_id"].strip().casefold(); returns the first matching call row
    or None. Task 3 never resolves by vessel name. For duplicate IDs, use
    the first CSV row retained by the shared loader. Returns None ->
    caller prints "Port call not found." and returns to menu.
- classify_shipment(shipment: dict) -> tuple[str, str]   [FIRM, new, owned
  by Task 3]
    Pure function, no I/O, no printing. Body is a straight if/elif/elif/else
    chain matching the rule table's order exactly, so an earlier true
    condition always wins and later conditions are never evaluated:

      def classify_shipment(shipment):
          if shipment.get("hazardous", False):
              return "CONTROLLED", "hazardous cargo"
          if shipment.get("temperature_controlled", False):
              return "COLD CHAIN", "temperature controlled"
          if shipment.get("priority") == "EXPRESS" or shipment.get("weight_kg", 0) >= 5000:
              return "EXPEDITE", "express service"
          return "STANDARD", "standard handling"

    Optional-field defaults follow the same absent-or-null-fails-to-default
    convention established in Task 1/Task 2: hazardous and
    temperature_controlled default to False (per DATA-DICTIONARY.md);
    priority and weight_kg are required fields per the data dictionary, so
    no default is defined for them by the spec, but the .get(...) calls
    above are defensive against a resolved-but-still-malformed record
    rather than a KeyError crash — this defensiveness is not a spec
    requirement, only a robustness choice, and should not silently invent
    business meaning (a shipment missing weight_kg is not expected to occur
    for any record that passed the shared shipment loader's required-field check,
    so this is belt-and-suspenders, not a documented edge case).
- build_priority_report(manifest, shipment_records) -> dict (or small
  dataclass) containing: an ordered list of (shipment_id, category, reason)
  tuples for each RESOLVED shipment_id (in manifest["shipment_ids"] order,
  unresolved ids simply skipped — no tuple, no line), and a totals dict/
  ordered structure pre-seeded with all four categories at 0 in table order
  (CONTROLLED, COLD CHAIN, EXPEDITE, STANDARD) before iterating, so a
  category with zero matches still exists in the totals structure and is
  still printed as "=0" rather than being absent from a dict that only ever
  gained keys it saw. Iterate manifest["shipment_ids"] in order and select
  the first valid record with each requested internal shipment_id from the
  shared shipment records; if none exists, continue without a line or count
  change. For a match, call classify_shipment(record), append the tuple,
  and increment totals[category]. Pure function over already-loaded data
  (no printing), consistent with Task 2's
  build_manifest_report being pure — main.py owns the actual print() calls.

main.py:
- In the `elif selection == 3:` branch: (1) load the shared call, manifest,
  and shipment results, retaining recoverable diagnostics for
  task-appropriate reporting; (2) prompt
  "Call ID: " (see Section 2 caveat on this exact string not being a
  confirmed client contract); (3) resolve via operations.resolve_call —
  on None, print "Port call not found." and return to the outer menu loop;
  (4) select the first usable manifest matching both call_id and vessel_id
  from the shared
  manifest records — if none, print "Manifest unavailable." and return to
  menu; (5) build the report via
  operations.build_priority_report and print each
  "{shipment_id} | {category} | {reason}" line in order, then print the
  "Category totals: CONTROLLED={n}, COLD CHAIN={n}, EXPEDITE={n},
  STANDARD={n}" summary line unconditionally (even if the manifest resolved
  zero shipments, so all four counts print as 0 with no cargo lines above
  them — see Section 4's empty-manifest case).
- Recoverable record diagnostics remain available to operations. Fatal
  source/CSV/schema/I/O failures propagate to an explicit, narrowly scoped
  service error path; do not collapse them into an unknown call, missing
  manifest, or empty successful report. Do not use a blanket `except:`.

Category-order guarantee (explicit, restated): totals must be seeded as an
ordered structure (e.g. a dict built as {"CONTROLLED": 0, "COLD CHAIN": 0,
"EXPEDITE": 0, "STANDARD": 0} up front, or four named counters) BEFORE the
classification loop runs, and the summary line must read from that fixed
order when printing — never derived by iterating "categories seen" (which
would omit zero-count categories) and never alphabetized or otherwise
resorted.
