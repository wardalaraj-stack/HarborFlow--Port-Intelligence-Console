2. TASK 9 REQUIREMENT SUMMARY (from the assignment PDF)
================================================================

BUSINESS OUTCOME: Build a reusable evidence index so operations can
retrieve prior incidents by keywords.

Exact Task 9 requirement:

Normalize all incident report text to lowercase words, removing punctuation
with regex. Build an inverted index whose keys are words and whose values
are lists of incident IDs containing that word. Also build a title lookup
whose keys are incident IDs and whose values are incident titles. Save both
structures in dataset/incident-index.json and load the cached file on later
runs.

Required top-level cache shape:

{
  "index": {
    "delay": ["INC-087", "INC-119"],
    "reefer": ["INC-102", "INC-119"],
    "temperature": ["INC-102"]
  },
  "titles": {
    "INC-087": "Gate congestion delay",
    "INC-102": "Reefer temperature deviation",
    "INC-119": "Reefer transfer delayed"
  }
}

Normalize the user’s query with the same rules. Score an incident by the
number of distinct query words whose index list contains its ID. Print only
positive matches, sorted by descending score and then incident ID. Use the
cached title lookup for the displayed title.

Exact demonstrated interaction/output:

  Search incident reports: reefer delay
  Matches for 'reefer delay':
  - INC-119 | score 2 | Reefer transfer delayed
  - INC-087 | score 1 | Gate congestion delay
  - INC-102 | score 1 | Reefer temperature deviation

Additional literal requirements:
- Do not add an incident ID twice to one word’s list when a word repeats in
  a report.
- Write valid JSON with exactly the top-level keys `index` and `titles`.
- Sort word keys, title keys, and every incident ID list.
- Before any cache decision, successfully discover a non-empty sorted list
  of source incident JSON paths and stat every source file; discovery/stat
  errors are fatal, and an empty source list is an explicit source-data
  error. If an existing cache has the exact valid schema and is fresh against
  all source mtimes, reuse it without parsing or reading incident JSON
  contents, even if those files would currently fail JSON or incident-schema
  validation. If the cache is missing, malformed, wrong-schema, or stale,
  rebuild it from source records.
- Searching must use the loaded index and title lookup rather than
  rereading incident reports.
- The query and report must use the same regex-based normalization rules.
- Print only positive matches; a zero-score incident must not appear.

The PDF does not prescribe the exact query prompt beyond the demonstrated
“Search incident reports: ” interaction, does not define an empty-query
message, and does not define diagnostics for unreadable/malformed source
incident files or invalid cache shapes beyond “malformed cache” requiring a
rebuild. These are integration decisions and are not presented as
additional PDF-mandated strings.

data_access.py:

  contract. Load every `.json` file
  under the relative path `dataset/incidents/`; do not hard-code the four

  `incident_id`, `call_id`, `title`, and `report`. Preserve strings as

  search scoring. During a rebuild, skip malformed source files only when at
  least one valid incident record remains. If no valid source incident
  records remain, fail explicitly and leave any existing cache untouched;
  never turn missing or unusable source data into an empty successful index.

text_tools.py:
- Provide one pure normalization helper used for both reports and queries,
  such as `normalize_words(text: str) -> list[str]`. Use the exact shared

  for scoring logic; the index builder must de-duplicate each incident ID

- Keep normalization free of I/O, cache reads, printing, and mutation of
  source records. Task 6’s sanitization helper must remain separate: do not
  replace the raw report with sanitized output before indexing.

operations.py:
- Provide a pure index builder such as
  `build_incident_index(incidents) -> {"index": ..., "titles": ...}`.

- Sort word keys, title keys, and each word’s incident-ID list before the

  `search_incident_index(cache, query) -> list[SearchMatch]`. Normalize
  the query with the same helper, collapse repeated query words before
  scoring, count one point for each distinct query word whose posting list
  contains the incident ID, discard zero scores, and sort by
  `(-score, incident_id)`.
- Use only the loaded cache in the scorer. It must not open incident JSON
  files or reconstruct titles from source records during a search.

main.py:

  `- {incident_id} | score {score} | {cached title}` in the required

- Return to the existing outer menu after the search, preserve options 1–8

5. SHARED-INTERFACE AND REUSE RISKS
================================================================

- Use the shared `load_json` and `LoadResult[Incident]` contracts in
  INTEGRATED-CONTRACT-PLAN.md. Preserve records and diagnostics at the
  data-access boundary; do not introduce a second incident directory walk.
  Task 9 needs the raw `report` and `title`; Task 6's sanitized text is an
  output artifact and must never replace the raw report for indexing.
- `dataset/incident-index.json` is unusual because it is a generated
  persistent file inside `dataset/`, while START-HERE.txt otherwise treats
  supplied dataset inputs as read-only. Task 9 explicitly authorizes this
  cache to be created/refreshed; do not generalize that permission to
  incident source files, weather, calls, manifests, shipments, or vessels.
- Cache freshness uses only source incident JSON modification times, never
  includes the generated cache in the source glob, and treats equal
  modification times as fresh. For every cache decision, discover a
  non-empty sorted source-file list and stat every source file first; if a
  listed source file disappears or cannot be statted, fail explicitly and
  leave the existing cache untouched. Rebuild from that sorted list when the
  cache is missing, malformed, wrong-schema, or stale.
- Cache validation must distinguish a valid cache from malformed JSON and
  wrong assignment schema. Per the coordinated contract in
  INTEGRATED-CONTRACT-PLAN.md, validate the exact `index` and `titles`
  top-level keys, required value types, and freshness only. Do not reject a
  sparse cache solely for unsorted entries or cross-map inconsistencies.
- Report normalization and query normalization must share one helper.
  Duplicating regex code in the index builder and search branch risks
  mismatched punctuation/case behavior and violates the reusable-index
  outcome.
- Search scoring must use distinct normalized query words. Otherwise a
  repeated query token can inflate scores beyond the PDF’s “number of
  distinct query words” rule.
- Title sorting/serialization and result sorting are separate contracts:
  cache title keys are sorted for JSON determinism, while result rows sort
  by descending score and then incident ID. Do not sort displayed results
  alphabetically by title.
- The index contains report words, not incident titles, as specified by the
  assignment. Titles are stored separately for display and must be read
  from the cached `titles` lookup during search.

9. INTEGRATION POLICY RESOLUTION
================================================================

Use the common loader, path, and source-error behavior in
INTEGRATED-CONTRACT-PLAN.md. Tokenize both source reports and queries with
the same exact expression:
`re.findall(r"[^\W_]+", text.casefold(), flags=re.UNICODE)`.
Underscores and punctuation delimit tokens; Unicode letters and digits are
included. For duplicate incident IDs, the first valid record in sorted
source-path order wins and later duplicates are diagnosed and skipped.

For every cache decision, first successfully discover a non-empty sorted list
of incident JSON source paths and stat every source file. Discovery or stat
errors remain fatal and explicit; an empty source-file list is an explicit
source-data error, not a reusable cache. Cache validation is limited to the
exact top-level `index` and `titles` objects, their required string/list
value types, and freshness against all discovered source mtimes. If an
existing cache has that valid schema and is fresh, reuse it without parsing
or reading incident JSON contents, even if those files would currently fail
JSON or incident-schema validation. Missing cache, malformed JSON, wrong
schema, and stale cache trigger rebuild; other cache I/O errors propagate.
Do not rebuild a sparse cache merely because postings are unsorted or
cross-map IDs are absent. Equal cache/source modification times are fresh
because the cache is not older. Rebuild serialization itself remains sorted
and deduplicated as mandated.

When rebuilding, load the discovered source records. Individual malformed
incident files may be skipped with diagnostics when at least one valid
incident record remains. If no valid source incident records remain, fail
explicitly and leave any existing cache untouched; do not write or present
an empty index as success. For duplicate incident IDs, the first valid
record in sorted path order wins and each later duplicate is diagnosed and
skipped. Use a same-directory temporary file followed by atomic replace for
cache writes, and surface write failures.

For a query that normalizes to no words, print
"Search query contains no searchable words." and do not score. For a
non-empty query with zero positive results, print the required heading
followed by "No matching incidents found."; print no zero-score rows.
These messages and the cache-validator boundary are project policies, not
additional PDF requirements. The exact worked search output and all other
mandated cache rules remain unchanged.
